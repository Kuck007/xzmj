## 0. 先给结论

这套系统最适合的不是模拟数据库主从，也不是给每台设备维护一条不能断的链，而是：

> **WebDAV 只保存不可变文件；每次本地变更打成一个加密 ChangeSet；任何完整 ChangeSet 都可以独立、乱序、重复应用；记录用外部 HLC 版本号解决冲突；快照只用于新机器初始化和以后压缩历史。**

保留此前已经确认、且合理的交互：

- 上传全自动、静默、加密，无“立即上传”按钮。
- 下载检查自动；真正合并由超管确认。
- 合并前验证系统密码，并先写 `Backups/bcom` 全量备份，保留 15 份。
- 手动全量备份/恢复逻辑保持不变；Auto 仍保留 10 份，手动备份不自动清理。
- 单构建，仅超管看到同步管理与合并入口。
- `User` 表不同步，账号与权限各机独立。

### 0.1 v3.0 推翻的旧设计

| 旧设计 | 新设计 | 为什么 |
|---|---|---|
| 每台设备一条 seq 必须连续的链 | ChangeSet 只要求 `changeId` 唯一，不要求连续 | 缺 #3 不妨碍应用 #4；#3 晚到也能补齐，不再因一个坏包冻结整台设备 |
| `appliedSeq` 水位、逐包 ack | `appliedChangeIds` 幂等集合 | 不依赖包顺序，天然支持断点、重放、乱序 |
| 缺包/坏包后上传 checkpoint 救链 | 只跳过并报告坏包，其余包继续；快照只用于初始化/压缩 | 不为存储异常制造全量写放大 |
| 给 10 个 @Model 增加 `updatedAt` | 同步版本放在外部 `SyncState`，业务模型不加字段 | 避免 SwiftData 迁移风险，也避免把同步机制泄漏进业务模型和旧备份 |
| 用 `updatedAt + deviceId` 做 LWW | 用 HLC `(wallMs, logical, writerId)` | 本机版本严格单调；同毫秒、时钟回拨、并发写入都有稳定全序 |
| 恢复自己的备份可继承 deviceId，并验链 | 每次恢复/重建都生成新 `writerId` | 旧写入者身份没有继承收益，只有双写撞号风险；旧数据仍然可读，不需要继承 |
| 应用标题就是同步身份 | `storeId` 才是身份，标题只是显示名 | 改标题不应迁移/切断数据；两个同名店也不会误合并 |
| 墓碑 180 天过期 | 墓碑不按时间过期 | 时间不能证明其他机器/旧备份已经知道删除；过期会复活已删记录 |
| 外键未到的记录跳过 | 先完整保存，等待关联记录后到 | 跳过就是永久丢单；当前模型本来就是 UUID 外键、无数据库关系约束 |
| 每次上传后完整下载回读 | PUT 成功 + PROPFIND size/ETag；下载时再完整 SHA256 | 去掉每次上传双倍流量，仍能在消费前发现损坏 |
| 每个包直接由本机系统密码派生密钥 | 每个 storeId 一个随机 storeKey，各机用同一个同步口令封装 | 系统密码与同步解耦；改密码不换数据密钥，新机接入只需同步口令 |
| 全量备份追加同步元数据 | 首版不改 `BackupPackage` | 恢复后统一走“新 writer + 云端对账”，旧备份格式完全不动 |
| 每日/03:00 才上传 | 保存后防抖上传（初始 20 秒，2026-11-21 起改为 3 分钟）+ 启动上传 + 失败重试；03:00 只做完整性扫描 | 新数据尽快到云端，同时减少碎片包并保留每日兜底 |

### 0.2 明确不做

- 不做实时推送、长连接、WebDAV LOCK、数据库级分布式事务。
- 不做字段级 CRDT。首版仍是**整行 LWW**；同一条记录两边同时改不同字段，较晚版本整行胜出，落败版本写冲突日志。
- 不做云端自动删除 ChangeSet。首版宁可多占空间，也不拿“所有机器都已收到”的假设冒险。
- 不在首版拆照片 blob。当前照片在 `PhotoRecord.init` 已压缩；先复用现有备份行。实际包体成为问题后再做内容寻址 blob，协议可扩展。
- 不引入第三方库，不改沙箱，不改现有全量恢复语义。

### 0.4 同步目录与命名（v3.3 定稿）

- 同步目录 = **`{应用标题}/sync`**（方案 §4.1 原设计）。当前 Debug 应用标题为「测试系统」→ 目录为 `测试系统/sync`。
- **最上层 `{应用标题}` 需用户在 WebDAV 服务器上手动创建**（服务器禁止新建第一层）；其下的 `sync` 子目录由 App 在启用同步时自动 MKCOL 创建。未命中时先 PROPFIND，缺失则自动创建并再次验证；仍失败会明确提示“请确认上一级目录已手动创建且账号有写权限”。
- 云端文件名**不加前缀**，严格按 §6.1：`store.json` / `key-{writerId}.json` / `change-*.enc` / `change-*.meta.json` / `snapshot-*`。
- 备份目录（`{应用标题}/backups`）与同步目录是两个独立目录，互不影响；「云端备份」列表只列备份目录，天然不会出现同步文件。
- Debug / Release 隔离依赖各自的应用标题：标题不同 → 目录不同。若两台构建标题相同，需先在设置里改标题，再启用同步。
- **fnOS（Go x/net/webdav）实测语义**：根 `/` 是只读的共享文件夹索引，根上 MKCOL / PUT 一律 405；一级目录必须在 NAS 后台建为“共享文件夹”；共享文件夹内部可读写，但一次只能建一级（多级同发返回 405 而非 409）；对已存在目录再 MKCOL 也返回 405。因此客户端必须逐级 MKCOL，并把 405 当作“可能已存在”，用 PROPFIND 验证后再继续。

## 1. 必须遵守的项目约束

开工前必须读 `AGENTS.md`。与本任务直接相关：

1. 只使用 `xcodebuild build ... -destination 'platform=macOS'` 验证，不用 archive。
2. 不改 entitlements，不动 Debug/Release 数据库路径。
3. 视图只显示和收集输入；差分、版本、合并、统计全部在 `AppCore` / `SyncEngine`。
4. 新 Swift 文件放在源码目录，`PBXFileSystemSynchronizedRootGroup` 会自动收录，不手改 pbxproj。
5. 默认 MainActor；网络、JSON、哈希、加密使用 `nonisolated`，不得跨线程触碰 @Model / ModelContext。
6. sheet 挂 body 根级别，不用 `.sheet(item:)`。
7. 未经用户明确要求，不提交业务代码，不发布版本。

### 1.1 本方案额外不变量

- **S1：没有完整 meta 的 enc 不是有效 ChangeSet。** enc 先传，meta 后传；消费者只认 meta。
- **S2：云端 ChangeSet 不可变。** 同一 `changeId` 永远对应同一字节；内容不同必须换新 `changeId`。
- **S3：ChangeSet 可乱序、可重复；包间允许部分成功。** 一个包坏，不阻塞其他包；失败项保持“未完整同步”提示，单包内部仍必须原子提交。
- **S4：记录身份只认 UUID。** 同名客户、同名订单不参与身份判断。
- **S5：同步版本不属于业务模型。** 不加 `updatedAt`，不改 `@Attribute(.unique)`，不改 Schema。
- **S6：任何读库失败都禁止上传。** 不能把“fetch 失败返回空数组”解释成整表删除。
- **S7：只有确认 `context.save()` 成功，才能提交 outbox。** 不允许 `try?` 吞掉保存错误后继续同步。
- **S8：远端合并不得形成同步回声。** 应用远端包时禁止写本地 outbox。
- **S9：外键缺失不丢记录。** 先落库，后到关联自然补齐；异常只报告。
- **S10：恢复后一律新 writer，且未完成云端对账前禁止上传。** 防止旧备份覆盖云端新数据或复活删除。
- **S11：合并非空本机库前，密码验证和 bcom 必须成功。** 任一步失败都不改业务数据。
- **S12：Debug 不碰正式同步空间。** 默认独立 `{title}-debug/sync` 与独立状态目录。

### 2.2 同步前必须止血

#### A. 保存错误不能被吞掉

当前 `AppCore.swift:619–648` 的 insert/delete/save 大量使用 `try? context.save()`；`Views/API/APIManager.swift:284/364` 也有相同问题。同步要求知道“到底保存成功没有”。

处理：

- AppCore 写入口改成 `throws`，或至少返回 `Result<Void, Error>`。
- 视图在保存失败时显示错误，不假装成功。
- 只有成功保存才调用 `SyncJournal`。
- API 同样不能保存失败仍返回 appointmentId / true。

不需要一次重写所有业务方法，但**所有会产生同步数据的写入口必须先做到错误可感知**。

#### B. 读取失败不能变成空表

当前 `AppCore.swift:236–239`：

```swift
return (try? context.fetch(descriptor)) ?? []
```

如果上传差分复用这个结果，一次读库异常就可能被判定为“全部删除”。

处理：

- UI 的容错读取可保留。
- 同步专用 `syncSnapshotRows() throws` 必须每张表 `try context.fetch`；任一表失败，整个上传中止。
- `AppCore.isReady == false`、正在恢复、正在合并时，禁止生成上传包。

#### C. 启动修复和 API 也纳入变更捕获

- `杏子美甲管理系统App.swift:419–437` 会直接修改订单/充值并保存。
- `APIManager` 使用独立 context 写入。

**v3.1：不再挂 DidSave 主捕获**。统一走「保存成功 → 20 秒防抖 → 全量哈希差分」，覆盖启动修复、API 独立 context、崩溃落在保存与状态写之间的全部情况。单一捕获路径即可满足正确性，无需每个写入口上报。

## 3. 总体架构

```text
本地 SwiftData
   │ save() 成功
   ▼
AppCore 同步快照（值类型 Backup* 行）
   ▼
SyncJournal
   ├─ 分配 HLC 版本
   ├─ 记录 upsert / tombstone
   └─ outbox 持久化
   ▼
SyncEngine（20 秒防抖 / 启动 / 失败重试）
   ├─ 全量哈希差分兜底
   ├─ 组装不可变 ChangeSet
   ├─ AES-256-GCM
   └─ WebDAV：先 enc，后 meta
                         │
                         ▼
                {syncRoot}/store.json
                {syncRoot}/change-*.enc
                {syncRoot}/change-*.meta.json
                {syncRoot}/snapshot-*.enc
                {syncRoot}/snapshot-*.meta.json
                         │
                         ▼
其他机器：列 meta → 找出未应用 changeId → 超管确认
       → 密码 → bcom → SHA256/解密 → 按记录版本合并
       → 每包 save → 记录 appliedChangeIds → refresh/repair
```

核心性质：

- 上传和下载合并不互相阻塞。普通运行中即使有待合并远端包，本机新变更仍可追加上传。
- 唯一禁止上传的状态是“恢复后尚未完成初始对账”以及“本机同步快照无法可靠读取”。
- 包没有顺序依赖。按 `createdAt + changeId` 排序只是为了界面稳定，不是正确性前提。

## 4. 身份与版本

### 4.1 storeId：一套店数据的身份

首次创建同步空间时生成 UUID，例如 `7D6E...`。云端 `store.json`：

```json
{
  "formatVersion": 3,
  "rulesVersion": 1,
  "storeId": "7D6E0FD6-...",
  "displayTitle": "杏子美甲管理系统",
  "createdAt": 1763635200.0
}
```

`formatVersion` 管同步包结构，`rulesVersion` 管合并后的确定性业务修复规则。两者任一高于本机支持版本，都必须停止消费并提示升级，避免新旧 App 用不同规则算出不同结果。

规则：

- 本地 `SyncState.storeId` 与云端不一致：停止同步，提示“目录属于另一套数据”，绝不自动合并。
- 默认 `syncRoot = {应用标题}/sync`，首次配置后把该路径保存在本地，不再随标题变化。
- 修改应用标题只更新显示名，不迁移云端。
- 真正换店时走独立操作“新建同步空间”：新 storeId、新目录或空目录、新 writer。

### 4.2 writerId：一次本地写入生命周期的身份

建议 10 位 base36，仅用于标识写入者与打破版本平局，不是机器指纹。

以下情况都生成新 writerId，并把 `writerSeq` 归零：

- 第一次启用同步；
- 全量备份恢复后；
- 删除/重建同步状态；
- 用户显式“重新接入同步”。

**没有继承流程，没有验链流程，没有原设备活跃检查。** writerId 变了不影响读取旧 ChangeSet，因为旧包按 changeId 和记录版本仍可消费。

### 4.3 HLC 版本号

```swift
struct SyncVersion: Codable, Comparable {
    var wallMs: Int64   // Unix 毫秒
    var logical: Int    // 同一毫秒/时钟回拨时递增
    var writerId: String
}
```

比较顺序：`wallMs` → `logical` → `writerId` 字典序。

本地生成：

```text
now = 当前 Unix 毫秒
if now > lastWallMs:
    wallMs = now; logical = 0
else:
    wallMs = lastWallMs; logical = lastLogical + 1
last = 新版本
```

收到远端版本后，按标准 HLC 规则推进本地时钟，保证本机后续版本不会小于刚见过的版本。

边界说明：HLC 能保证确定全序和单 writer 单调，不能让错误系统时钟变成真实时间。若 WebDAV HTTP Date 与本机相差超过 5 分钟，状态页提示校时；不要为了“看起来合理”偷偷改业务日期。

### 5.2 SyncState

```json
{
  "formatVersion": 3,
  "storeId": "7D6E...",
  "syncRoot": "杏子美甲管理系统/sync",
  "writerId": "k3f9a2mnop",
  "writerName": "kuck 的 Mac mini",
  "writerSeq": 43,
  "lastWallMs": 1763635200123,
  "lastLogical": 2,
  "records": {
    "customers": {
      "UUID": {
        "version": {"wallMs": 1763635000000, "logical": 0, "writerId": "k3f9a2mnop"},
        "deleted": false,
        "syncedHash": "sha256-of-current-synced-row",
        "pendingChangeId": "01J...",
        "pendingHash": "sha256-of-pending-row"
      }
    }
  },
  "appliedChangeIds": ["01J...", "01J..."],
  "latestSnapshotId": null,
  "recoveryRequired": false,
  "lastUploadAt": 1763635200.0,
  "lastCheckAt": 1763635200.0,
  "lastMergeAt": 1763635200.0
}
```

职责（每条记录只占一行，避免多表交叉写导致的状态矛盾）：

- `version`：本机当前已知的获胜版本，含墓碑；用于冲突判断。
- `deleted`：墓碑标记，永久保留。
- `syncedHash`：已成功上传或从远端应用后的行内容哈希（nil = 从未同步）；是全量差分发现遗漏修改/删除的唯一依据。
- `pendingChangeId`：已组进 outbox、尚未确认云端提交；nil 表示无待确认上传，防止差分重复造包。
- `pendingHash`：待确认包内该行的内容哈希，用于差分包时跳过“已经打包过且内容未变”的行。
- `appliedChangeIds`（全局）：已经成功落库的包 id，保证重复下载不重复应用。
- `pendingBatchIds` 不落盘：由扫描 `outbox/` 目录得出。

状态写盘必须原子；任何字段失败都不能继续假装成功。`appliedChangeIds` 首版完整保留，不能用“最近 N 个”代替，否则旧包会重复消费。

### 5.3 outbox 与崩溃恢复

1. 本地保存成功后触发 3 分钟防抖；防抖到期做全量差分，把发现的变更组成不可变 outbox 包。
2. outbox 先落盘，再进入上传队列。
3. 上传未确认前，包内容不变、changeId 不变。
4. 云端提交成功后，才更新 `syncedHash`、清空 `pendingChangeId`、删除 outbox。
5. 崩溃发生在“云端成功、状态未写”之间：重启后用同一 changeId 重试；若远端同名 meta 的 size/sha 与本地一致，直接视为成功，不重复制造包。
6. outbox 丢失但 `syncedHash` 尚未推进：全量差分能重新发现这些变化并造新 changeId，不丢数据。

## 6. 云端数据契约

### 6.1 ChangeSet 文件命名

使用平铺目录，适配现有 `PROPFIND Depth:1`，避免递归列目录。目录为 `{应用标题}/sync`（见 §0.4）。

```text
change-{writerId}-{seq6}-{changeId}.enc
change-{writerId}-{seq6}-{changeId}.meta.json
snapshot-{snapshotId}.enc
snapshot-{snapshotId}.meta.json
key-{writerId}.json
store.json
```

- `writerSeq` 只是本机计数和显示信息，**不要求连续，不参与“是否漏包”的判断**。
- `changeId` 使用随机 UUID 去横线，或等强度随机 ID；文件是否已应用只看 changeId。
- `seq6` 到 999999 后仍可继续用更宽数字；解析器不要硬限六位，更不要因此停同步。

### 6.2 ChangeSet 解密后的结构

不用 JSONValue 万能字典，使用强类型泛型：

```swift
struct VersionedRow<Row: Codable>: Codable {
    var version: SyncVersion
    var row: Row
}

struct ChangeSet: Codable {
    var formatVersion: Int       // 3
    var rulesVersion: Int        // 合并后业务修复规则版本
    var storeId: String
    var changeId: String
    var writerId: String
    var writerSeq: Int
    var createdAt: Double

    var customers: [VersionedRow<BackupCustomer>]
    var technicians: [VersionedRow<BackupTechnician>]
    var serviceCategories: [VersionedRow<BackupServiceCategory>]
    var serviceItems: [VersionedRow<BackupServiceItem>]
    var records: [VersionedRow<BackupServiceRecord>]
    var appointments: [VersionedRow<BackupAppointment>]
    var orders: [VersionedRow<BackupOrder>]
    var inventoryItems: [VersionedRow<BackupInventoryItem>]
    var commissionRules: [VersionedRow<BackupCommissionRule>]
    var lashReminders: [VersionedRow<BackupLashReminder>]
    var rechargeRecords: [VersionedRow<BackupRechargeRecord>]
    var reconciliations: [VersionedRow<BackupDailyReconciliation>]
    var deletes: [Tombstone]
}

struct Tombstone: Codable {
    var entity: String
    var uuid: UUID
    var version: SyncVersion
}
```

所有数组在解码时缺省为空。`formatVersion` 或 `rulesVersion` 高于本机支持版本时，必须拒绝并提示升级，不能静默忽略未知实体或沿用旧业务修复规则。

`Backup*` 行结构保持原样；同步版本在 `VersionedRow` 外包装，不写进业务行。

### 6.3 meta

```json
{
  "formatVersion": 3,
  "storeId": "7D6E...",
  "changeId": "01J...",
  "writerId": "k3f9a2mnop",
  "writerName": "kuck 的 Mac mini",
  "writerSeq": 43,
  "createdAt": 1763635200.0,
  "counts": {"upsert": 14, "delete": 3},
  "sha256": "enc 原始字节的 SHA256",
  "size": 84213,
  "keyId": "a1b2c3d4",
  "fileName": "change-k3f9a2mnop-000043-01J....enc"
}
```

明文 meta 不含客户姓名、手机号、金额。`keyId` 只标识本套店的 storeKey，不能据此推导密钥。

### 6.4 Snapshot

Snapshot 是某一时刻的完整同步视图：

```swift
struct SyncSnapshot: Codable {
    var formatVersion: Int
    var rulesVersion: Int
    var storeId: String
    var snapshotId: String
    var createdAt: Double
    var rows: BackupPackageBusinessRows   // 12 表，不含 User/appSettings
    var records: [String: [String: RecordVersionState]]
    var includedChangeIds: [String]
}
```

`BackupPackageBusinessRows` 可以复用 12 组 `Backup*` 数组，不需要修改现有 `BackupPackage`。

Snapshot 必须包含：

- 当前所有未删除记录；
- 当前全部墓碑及版本；
- 导出时已经体现进快照的**精确 changeId 集合**。

消费 Snapshot 后，跳过 `includedChangeIds`，其余晚到/未包含的 ChangeSet 仍可独立应用。不能只用“writer 最大 seq”表示覆盖范围，因为本设计允许乱序与晚到。空库初始化可直接导入；非空库应用 Snapshot 时，仍按第 8 节的记录版本与墓碑规则逐条合并，不能整包覆盖。

Snapshot 用途仅限：

1. 首次把一台现有机器发布为云端种子；
2. 新机器快速初始化；
3. 将来人工确认后的云端历史压缩。

**不存在“链断了所以必须 checkpoint”的路径。**

### 6.5 同步密钥与钥匙封装

每套店在首次创建同步空间时生成一次随机 32 字节 `storeKey`。所有 ChangeSet/Snapshot 都用它做 AES-256-GCM；`BackupManager.encryptBackup/decryptBackup` 的文件格式仍可复用，只是密钥不再由某一台机器的系统密码直接派生，改由同步口令派生。

本地：

- `storeKey` 存 macOS Keychain，service 使用独立前缀，account 为 storeId。
- 不写 `sync-state.json`，不写日志，不进入全量备份。

云端每个 writer 有一个可覆盖的钥匙信封（它不是 ChangeSet，不受不可变规则限制）：

```text
key-{writerId}.json
```

```json
{
  "formatVersion": 3,
  "storeId": "7D6E...",
  "writerId": "k3f9a2mnop",
  "keyId": "storeKey 的 SHA256 前 8 位 hex",
  "wrapKeyId": "同步口令派生 KEK 的标识",
  "wrappedStoreKey": "用同步口令派生的 KEK 做 AES-GCM 加密后的 storeKey",
  "updatedAt": 1763635200.0
}
```

- v3.1：KEK 来自**同步口令**（超管首次启用同步时设置，8 位以上，独立于任何一台机器的系统密码），不再使用各机系统密码。
- 首台机器：生成 storeKey → 存本机 Keychain → 用同步口令派生 KEK 封装 → 上传 `key-{writerId}.json`。
- 新机器：任选一个云端钥匙信封，输入**同步口令**解封一次 → 把同一 storeKey 存进本机 Keychain → 再用同一口令生成自己的信封。
- 日常合并仍验证本机系统密码作为操作授权，数据包统一用 storeKey 解密；不存在逐包“旧密码”流程。
- 任意机器修改系统密码：与同步完全无关，无需重封装任何信封。
- 修改同步口令：各机用旧口令解封 → 用新口令重新封装并覆盖自己的 `key-{writerId}.json`；历史 ChangeSet 不需重加密。
- 恢复产生新 writerId 后，可复用本机 Keychain 中同 storeId 的 storeKey；若本机没有，则用同步口令解封。
- 所有已接入机器的口令都遗失且本机 Keychain 也没有 storeKey 时，云端数据无法解密。这是加密的真实边界，不提供后门。

`meta.keyId` 因此是稳定的 storeKey 标识，不再是密码版本标识。

## 7. 本地变更捕获与上传

### 7.1 单一捕获路径：全量哈希差分

v3.1 起**不再由 AppCore 在每个写入口上报变更**。统一为：任何一次 `save()` 成功后做 3 分钟防抖（2026-11-21 起由 20 秒调整），然后对 12 表做值类型快照、逐行计算哈希，与 `syncedHash` 比对。

依据（2026-11-20 实测）：Debug 库 6332 行全量差分 **108ms**；正式库 773 行按同比例约 **13ms**。单一路径同时覆盖视图表单、启动修复、API 独立 context、崩溃落在保存与状态写之间等全部情况。代价只是新数据最多延迟 3 分钟进云（防抖上限，用户可接受）。

> 两个已踩过的性能坑（阶段 1 自检发现）：
> 1. 行哈希早期用 `String(format: "%02x", byte)`，每行 32 次格式化，6332 行额外消耗约 200ms → 改为查表拼 UTF-8。
> 2. 状态写入早期是「取出内层字典 → 改 → 写回」，每次写触发整表 copy-on-write，退化成 O(n²) → 改为 `records[entity, default: [:]][id] = value` 原地写。
>
> 阈值：正式库超过约 6000 行（差分 >100ms）时，再考虑把差分搬到后台线程。

| 当前快照 | syncedHash | 判定 |
|---|---|---|
| 有记录 | 无 | 新增；若 pending 已有则跳过 |
| 有记录，hash 不同 | 有 | 修改；若 pending 已是同 hash 则跳过 |
| 有记录，hash 相同 | 有 | 无变化 |
| 无记录 | 有 | 删除，生成墓碑 |
| 无记录 | 无 | 无变化 |

差分发现的变更分配新的 HLC，并记为“由差分捕获”。`pendingChangeId` 非空且哈希相同的行直接跳过，避免重复造包。

哈希：

```text
JSONEncoder.outputFormatting = [.sortedKeys]
dateEncodingStrategy = .secondsSince1970
对原始 Backup* 行编码，SHA256
```

不把 HLC、writerId、changeId 混入行哈希。数组顺序保持业务原顺序；照片 Data 参与哈希。

### 7.2 上传触发

| 触发 | 行为 |
|---|---|
| 本地保存成功 | 3 分钟防抖；连续录入合并成一批（2026-11-21 起由 20 秒调整为 3 分钟，减少碎片包） |
| App 启动完成 | 30 秒后检查 outbox 并上传 |
| 上传失败 | 1/5/15 分钟退避；下次启动立即重试 |
| 每天 03:00 / 下次启动补做 | 全量哈希差分 + outbox 上传，不强制每天造包 |
| 超管手动按钮 | 不提供 |

上传前必须同时满足：WebDAV 已配置、系统密码存在、storeId 匹配、AppCore 就绪、非恢复待对账、12 表同步快照全部读取成功。

### 7.3 上传步骤

1. 若没有 pending 且兜底差分为空，结束，不占 writerSeq。
2. 组 ChangeSet，`writerSeq += 1`，生成 changeId；写 outbox。
3. JSON 编码 → 用本机 Keychain 中的 storeKey 加密 → 计算 enc SHA256/size → 写 meta。
4. PUT enc，建议带 `If-None-Match: *`；服务器不支持也不影响随机 changeId 的唯一性。
5. PROPFIND 验证 enc size；若同 changeId 已存在且 sha/size 相同，按幂等成功处理。
6. PUT meta，再验证 meta 可读且关键字段一致。
7. 更新本地 `syncedHash`/`pendingChangeId`/`appliedChangeIds`，删除 outbox。
8. 上传失败保留 outbox；下次仍用同 changeId，不产生重复业务数据。

不要求每次上传后完整下载。下载合并前一定做完整 SHA256，因此坏包不会落库。

### 7.4 空包与删除安全

- 空 ChangeSet 不上传。
- 任一表 fetch 失败、快照行解码失败、哈希失败：整批中止。
- 墓碑生成必须以“可靠上一次 `syncedHash` 有、可靠当前快照无”为依据，不能使用 UI 内存数组的异常空值。

## 8. 检查、下载与合并

### 8.1 检查

- 启动后、App 更新检查后、超管点“检查云端更新”时执行。
- 一次 PROPFIND 获取目录；只解析符合规则的 meta。
- 与本地 `appliedChangeIds` 比较，下载未应用 meta（通常很小）。
- 只有 enc 没有 meta：视为未完成上传，忽略；超过 24 小时可在状态页报告孤儿文件。
- 有 meta 没有 enc：列为异常包，不影响其他包。
- 检查结果只对超管弹汇总；其他角色不打扰，上传仍可后台进行。

### 8.2 合并确认与密码

非空本机库合并前：

1. 超管确认汇总。
2. `SecurityManager.verifyPassword` 验证当前系统密码。
3. 导出全量到 `Backups/bcom/{应用名}-合并前-yyyyMMdd-HHmm.json`，按当前密码加密。
4. 回读并解码验证 bcom；失败立即中止。
5. bcom 保留 15 份；不得占用 Auto 的 10 份配额，也不清理手动备份。
6. 磁盘不足或备份失败，不下载应用任何包。

空库首次从云端初始化不必制造空 bcom，但仍需超管与密码确认。

### 8.3 每包处理

1. 下载 enc 到 incoming，复用断点续传。
2. 校验 size + SHA256。
3. 用本机 Keychain 中该 storeId 的 storeKey 解密；没有 storeKey 时先走一次钥匙信封接入流程。
4. 校验 formatVersion/rulesVersion/storeId/changeId/writerId 与 meta、store.json 一致。
5. 若 changeId 已 applied：标记成功并跳过。
6. `AppCore.syncApply(changeSet)`：先置 `isApplyingRemote = true`，逐条版本比较，整包一次 save。
7. save 成功后记录 appliedChangeIds，并更新受影响记录的 `version`/`deleted`/`syncedHash`，同时清空这些记录的 `pendingChangeId`。
8. 全部包处理完毕后再统一收尾：`isApplyingRemote = false` → `repairAfterRemoteMerge()` → **一次** refresh。合并过程中 `refresh()` 只物化 + 重算，不写库、不记 journal，因此不会产生回声，也不会做 N 次补睫扫描。
9. 任何包失败：记录失败原因，继续其他独立包；汇总页明确“尚有 N 包未成功”，不能显示全部同步完成。

崩溃在业务 save 与状态写之间：下次重放该包。版本比较和内容相同判断使其幂等。

### 8.4 upsert 判定

设 `incoming.v` 与本地 `records[entity][uuid]`：

| 情况 | 动作 |
|---|---|
| 本地无版本 | 插入；记录 incoming 版本与 syncedHash |
| incoming.v > local.v | 覆盖整行；更新版本/syncedHash；若本地有未同步不同内容，写冲突日志 |
| incoming.v < local.v | 保留本地；若内容不同，写冲突日志；本地 pending/上传资格不变 |
| 版本相同、内容 hash 相同 | 幂等跳过 |
| 版本相同、内容不同 | 协议异常，拒绝该行并报告；不能靠猜选一个 |
| 本地是更新墓碑 | 按同一版本比较，较旧 upsert 不得复活 |

远端覆盖本地后，若 outbox 中该记录版本更旧，标记 superseded 并移除；若本地 pending 版本更新，则保留。

### 8.5 delete 判定

| 情况 | 动作 |
|---|---|
| 本地无记录 | 保存墓碑与版本；重复执行无副作用 |
| 墓碑版本 >= 本地记录版本 | 删除本地记录，保留墓碑；清空该行 syncedHash |
| 墓碑版本 < 本地记录版本 | 保留本地，记冲突；本地之后仍可上传 |
| 同版本重复墓碑 | 幂等跳过 |

墓碑永久保存在本地 `records` 中，并进入后续 Snapshot。没有 180 天自动过期。

### 8.6 更新记录的方式

为 12 个模型实现 `apply(from backupRow)`：

- 已存在记录逐字段赋值，不 delete+insert，避免唯一约束冲突。
- UUID 不允许改变。
- 新记录使用现有 `convenience init(from:)`。
- 整包结束一次 `try context.save()`；失败 rollback，不推进 appliedChangeIds。
- 不修改 `BackupManager.apply` 的全量恢复行为。

## 9. 外键与业务一致性

### 9.1 外键缺失绝不跳行

当前 SwiftData 模型用 UUID 外键，没有数据库关系约束。订单、预约、服务记录应先完整保存。客户/技师/项目稍后到达后，现有 Map 查找即可恢复显示。

处理：

- 合并报告可列“当前仍有 N 个悬空引用”。
- 不阻塞包，不删除记录，不改外键，不把订单金额归零。
- UI 对缺失名称显示“未知/待同步”，不能因此崩溃或隐藏到无法修复。

### 9.2 合并后的确定性修复

远端按行合并后，不能只刷新列表。新增 `AppCore.repairAfterRemoteMerge()`，统一执行：

1. 重新物化与共享 Map、仪表盘、客户聚合。
2. 运行补睫「缺提醒」逻辑，但必须在远端应用模式下，并且：
   - 只做缺失提醒的创建，新建提醒的 id 必须用 `LashReminder.derivedID(orderId:)` 派生 —— 两台机器对同一订单算出同一条记录，HLC 自然收敛，不会出现两条重复提醒；
   - **不做**「按客户 + 服务项目反查订单补 orderId」这一步：该匹配依赖数组顺序，结果不确定；此关联只允许在本地业务命令里完成；
   - 手动提醒（`orderId == noOrderID`）不参与任何自动修复。
3. 校验已知派生状态：例如 `NailServiceRecord.isPaid` 与订单关联、预约闭环状态；修复规则必须 deterministic、幂等。
4. 修复完成后，把受影响记录的 `syncedHash` 统一更新为当前内容，防止各机把相同派生修复反复回传。

充值、订单、删除级联仍由本地 AppCore 业务命令产生一组最终行变化；同步复制这些行，不在远端重新执行 checkout/deleteOrder，避免重复级联。

首版不承诺自动解决所有跨行业务语义冲突；真正无法确定的冲突保留双方快照，由人工处理。bcom 是最后兜底。

## 10. 首次接入、恢复与新机器

### 10.1 第一台机器（云端为空）

1. 创建 storeId、writerId、随机 storeKey、钥匙信封、store.json。
2. 若本机有数据，生成 Snapshot：全量行 + 初始 HLC 版本 + 空 includedChangeIds。
3. 静默上传钥匙信封与 Snapshot；成功后记录各行的 syncedHash。
4. 后续只上传 ChangeSet。

### 10.2 新机器（本机为空，云端有数据）

1. 输入 WebDAV，读取 store.json；通过任意云端钥匙信封接入 storeKey，并验证本机超管系统密码作为操作授权。
2. 生成全新的 writerId，保存本机钥匙信封。
3. 下载最新 Snapshot；没有 Snapshot 则重放全部 ChangeSet。
4. 超管确认后初始化本机。
5. 应用 Snapshot 未覆盖的 ChangeSet。
6. 完成后才开放上传。

### 10.3 两台都已有各自历史数据

不要静默合并两套店数据。提供明确选择：

- **推荐**：先选一台为种子，另一台先手动备份，再清空本机后从云端初始化。
- **高级合并**：按 UUID + HLC 合并，但没有版本的历史记录统一视为“旧版本”，并完整记录冲突；结果必须人工抽查。

同一笔业务在两台各录一次会得到不同 UUID，同步无法识别为同单，这不是技术去重能可靠解决的问题。

### 10.4 全量备份恢复

`BackupPackage` 和 `BackupManager.apply` 不改。恢复结束后调用 `SyncEngine.handleFullRestore()`：

1. 停止上传并清空 outbox/pending。
2. 生成新 writerId。
3. 清空本地 records（含 syncedHash）与 appliedChangeIds，设置 `recoveryRequired = true`。
4. 若连接已有云端：先下载 Snapshot + ChangeSet 对账。恢复库中没有同步版本的记录视为最旧，云端新版本/墓碑优先。
5. 对账完成后，再为恢复库中仍然独有、且未被墓碑删除的记录分配新版本并上传。
6. 若明确创建全新同步空间，才把恢复库作为种子 Snapshot。

**没有“恢复自己的包就继承 writerId”这条路径。** 用户若想让旧备份完全覆盖云端，应使用单独的“以本机为准新建同步空间”，而不是普通恢复。

## 11. 安全、界面与存储

### 11.1 安全

- ChangeSet/Snapshot 使用随机 storeKey + AES-256-GCM；各机用同一个**同步口令**封装同一 storeKey，复用现有备份加解密格式。
- storeKey 只存 Keychain；日常上传直接读取本机 Keychain，不需要输入密码，也不存在逐包旧密码尝试。
- 合并时仍用本机系统密码做操作授权；bcom 继续使用本机密码加密，与同步 storeKey 相互独立。
- 密码不写日志、不写状态文件；钥匙信封只包含封装后的密钥，不包含明文 storeKey。
- meta 只有技术信息，不含业务字段。
- SHA256 用于损坏检测，AES-GCM 用于密文完整性；不要把明文 sha 当成防恶意伪造的签名。

### 11.2 设置页

仅超管显示“增量同步”：

```text
同步空间       杏子美甲管理系统（storeId 尾号）
本机写入者     kuck 的 Mac mini（writerId）
待上传         2 包 / 14 条
云端更新       3 包可合并，1 包异常
上次上传       11-20 21:32
上次合并       11-20 21:35

[检查云端更新] [合并云端数据] [查看异常] [冲突记录]
```

无“立即上传”。合并 sheet 显示各包条数、大小、异常原因；成功结果包含 bcom 文件名。

### 11.2.1 启动检查与快速合并（2026-11-21 落地）

- **触发**：登录后 `startAfterBootstrap`；等 Sparkle 更新周期结束（`didFinishUpdateCycleFor`）后 2 秒执行，30 秒内没结束则兜底执行；每个登录会话只检查一次。检查只做 PROPFIND + 读 meta。
- **提示**：检查到未应用包时按角色弹窗——超管/管理员提示合并，技师提示「请使用管理员或超管账号登录」；两种情况都在设置图标显示红点，并出现独立的「待同步」胶囊（技师点击只提示登录）。
- **快速合并**：超管/管理员点胶囊或弹窗「立即合并」→ `QuickMergeSheet`，输入系统密码后直接合并；仍走 `mergeCloud`（bcom 备份 → 校验 → 应用 → repair）。
- **红点持久化**：UserDefaults `sync.pendingMergeBadge`；合并成功、检查结果为空、停用同步时清除；断网/合并失败保留。
- **更新窗口避让**：Sparkle 正在展示更新窗口时只挂起弹窗，窗口关闭后再弹，检查本身照常进行。
- **权限**：设置页同步区块仍仅超管可见；`mergeCloud` 内部增加超管/管理员角色守卫，技师无法调用。
- **检查性能（2026-11-21）**：一次 PROPFIND 的文件列表在本次检查/合并中复用，不再为每个 meta/enc 重复列目录；已应用包按文件名里的 changeId 直接跳过下载，未应用的 meta 用 3 并发下载（已实测 NAS 接受）；合并复用检查结果，不再重复下载 meta；单个 meta 读取失败只跳过并记录，不再让整次检查静默失败；下载临时文件读取后立即删除，避免 `incoming/` 堆积。
- **合并批量应用（2026-11-21）**：先逐包下载/校验/解密（最多 8 并发，公网延迟受限实测 6 并发约 4.4 倍加速；单包失败只跳过），再整批一次构建表字典、一次 `save`、一次 `reload`；不再每个包都全量重载 12 张表（50 个包曾因此耗时约 4 分钟）。
- **上传防抖**：由 20 秒改为 3 分钟 trailing 防抖，减少一次连续操作被拆成多个碎片包；启动补传与失败退避（1/5/15 分钟）不变。

### 11.3 云端保留策略

首版：

- ChangeSet 不自动删除。
- Snapshot 自动保留最近 2 份；最新 Snapshot 任何情况下不可删。
- 不做 ack 驱动清理，不做 dormant 推断，不做 30/90 天删数据。
- 状态页展示云端文件数与总大小。

当文件数量真的影响 PROPFIND 性能时，再增加“整理云端”：

1. 生成包含精确 includedChangeIds 的新 Snapshot；
2. 所有在线机器确认已应用该 Snapshot；
3. 人工确认后才删除被覆盖的 ChangeSet；
4. 墓碑必须继续保留在 Snapshot 中。

清理只是性能优化，永远不是同步正确性的前提。

## 13. 失败矩阵

| 场景 | 行为 |
|---|---|
| 本地 save 失败 | 显示错误，不写 outbox |
| 任一表 fetch 失败 | 整批上传中止，不产生删除 |
| enc 上传成功、meta 失败 | 本地删除 outbox（状态未推进）；重试重新差分生成新 changeId；云端无 meta 的 enc 被消费者忽略，24h 后在状态页报告孤儿 |
| 云端成功、本地状态未写 | 同 changeId 重试，sha/size 一致即幂等成功 |
| changeId 相同但 sha 不同 | 拒绝覆盖，报告本地/云端异常，换 changeId 重建 |
| #1、#3 存在，#2 不存在 | 正常应用 #1/#3；不判链洞 |
| #2 一周后才到 | 正常应用；记录版本自动决定最终状态 |
| 某包 sha/解密失败 | 跳过该包，其他包继续；状态保持“未完整” |
| 外键记录晚到 | 子记录先保留，父记录到后自然恢复 |
| 同记录双机同时修改 | HLC 整行 LWW，双方快照写冲突日志 |
| 删除与修改冲突 | 版本大者胜，墓碑不提前过期 |
| 合并中途强退 | 已提交包幂等，未提交包下次重放 |
| 恢复旧备份 | 新 writer；先对账，云端新删除不复活 |
| 修改应用标题 | 只改显示名，不动 syncRoot/storeId |
| 修改本机系统密码 | 无需任何同步操作，历史包仍可解密 |
| 本机 Keychain 丢失 storeKey | 暂停同步；通过其他设备的钥匙信封重新接入，不跳过解密 |
| format/rules 版本高于本机 | 停止消费并提示升级，不用旧规则猜解新包 |
| 远端 storeId 不匹配 | 停止同步，不自动建包 |
| 云端被清空 | 视为另一套空空间；人工选择重新发布 Snapshot，不静默覆盖 |

### 阶段 3：拉取与合并（代码已完成 2026-11-20）

- meta 检查、下载校验、密码门、bcom、SyncApplier、冲突日志、repair。

**实施记录**

- `checkCloud()`：PROPFIND → 只下载 `change-*.meta.json` → 过滤已 applied → 按 createdAt 排序；同时报告「有 enc 无 meta」的孤儿文件。
- `mergeCloud(password:)`：系统密码校验 → **bcom 全量加密备份**（`Backups/bcom`，保留 15 份，不占 Auto 配额）→ 逐包下载并按 size + SHA256 校验 → storeKey 解密 → storeId/changeId/format/rules 四重校验 → `AppCore.syncApply` → 记录 appliedChangeIds。单包失败不阻塞其他包，失败原因写冲突日志。
- `SyncApplier`：整行 LWW（版本大者胜，同版本跳过）；墓碑版本 ≥ 本地版本才删；已存在记录**逐字段更新**，不 delete+insert；整包一次 save；每包后重新物化，避免下一包对同一 UUID 重复 insert。
- 合并期 `isApplyingRemote = true`：`save()` 不通知上传、`refresh()` 不触发补睫写库，杜绝回声；全部包结束后统一 `repairAfterRemoteMerge()`（物化 + 重算 + 一次补睫缺提醒修复）。
- 冲突日志：`~/Library/Application Support/xzmj/conflicts[/Debug]/YYYY-MM.jsonl`。
- 设置页：检查云端更新、待合并包数与体积、系统密码输入、合并结果（含 bcom 文件名与失败包数）。

**已知边界**

- 端到端双机合并依赖阶段 4：新机必须先“采用云端 storeId + Snapshot 初始化”，当前 enable 对已有云端数据但 storeId 不同的情况会明确拒绝（不自动合并）。
- repair 首版只创建缺失补睫提醒（派生确定性 ID），不反向补 orderId。
- 合并后由 repair 产生的新行会作为一次本地变更上传（幂等收敛，不会重复业务数据）。

验收：乱序、重复、坏包、删除冲突、外键晚到、合并回声——需阶段 4 完成后双机联调。

### 阶段 4：恢复与初始化（已完成 2026-11-21）

- 新 writer、恢复对账、新机 Snapshot 初始化、标题与 storeId 解耦。

**实施记录**

- **新机接入**：启用时读取云端 `store.json`；若本机没有任何业务数据，则采用云端 `storeId`、生成新 `writerId`、用同步口令解封任一云端信封取回 `storeKey`；随后下载最新 Snapshot（按 `SyncSnapshotMeta.createdAt`）转成 ChangeSet 走同一合并逻辑，再补齐快照之后的包，最后统一 repair 一次。
- **安全边界**：本机已有业务数据且 `storeId` 不一致时**明确拒绝**，绝不自动合并两套店数据；接入已有同步空间需要超管系统密码授权。
- **恢复对账**：全量备份恢复成功后调用 `handleFullRestore()` —— 生成新 writerId、清空 `records`/`appliedChangeIds`、`recoveryRequired = true`、清空 outbox、停止上传；用户重新输入同步口令启用时，先拉 Snapshot + 未应用包对账（云端新版本/墓碑优先），完成后再开放上传。
- **标题与身份解耦**：`syncRoot` 首次启用后固化在本地状态，改标题只影响显示名，不迁移云端目录。

**待联调**：双机端到端（新增 / 修改 / 删除墓碑 / 乱序 / 坏包 / 恢复）。

**联调结果（2026-11-21，Debug ↔ Release 双机，fnOS WebDAV）**

- ✅ 新机接入：采用云端 storeId + 新 writerId，自动创建 `{标题}/sync`，下载 Snapshot 完成初始化（6339 行），状态空闲。
- ✅ A 新增 → B 检查云端 → 密码合并 → 数据出现。
- ✅ B 修改 → 20 秒防抖自动上传 → A 检查并合并 → 修改生效。
- ✅ A 删除 → 墓碑上传 → B 合并 → 记录消失。
- ✅ 旧备份恢复后对账：B 导入「删除前」的备份使其复活 → 重新启用同步时自动按墓碑删除（云端版本较新优先），无需手动操作；随后「检查云端」显示无待合并更新。
- ✅ 双机同时改同一记录：整行 LWW，版本较晚的一方胜出，较早的整行被覆盖（非字段级合并）；较早侧合并时写冲突日志。
- ✅ 断网重试：断网后连续多次编辑，恢复网络后只产生 1 个包并上传成功；「待上传」归零、无孤儿包。
- ✅ 防抖语义确认：保存后 20 秒 trailing 防抖——20 秒内继续操作会顺延，直到连续 20 秒无写入才打包上传，不会累积多个小包。
- 已修问题：全新安装自带 9 条默认种子被误判为“已有业务数据”，现识别为纯净安装并先清空再接入；设置页「合计」口径遗漏 4 张表，已补全为 12 表；上传失败残留 outbox 导致「待上传 1」，现失败即删本次包并由 `refreshPendingCount` 清理孤儿。
